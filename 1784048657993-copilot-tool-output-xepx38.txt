# AGT × RVAS × Citadel — Conceptual Intersection Report

> **Scope:** Conceptual comparison only. This is not an implementation plan,
> not a deployment guide, and not a compliance certification. All AGT
> compliance documents cited here are self-assessments; AGT itself is
> **Public Preview** software.

---

## Executive Summary

Three distinct Microsoft artefacts address AI-agent governance from different
angles. **RVAS AI Governance** is a co-delivered *programme* — seven facilitated
sessions that leave ownership records, evidence artefacts, and a maturity
scorecard in the customer's own environment. **Foundry Citadel Platform** is a
*reference architecture and deployable platform accelerator* that routes
approved AI traffic through Azure API Management, applies shared gateway-level
runtime safeguards, and records telemetry. **Agent Governance Toolkit (AGT)** is
an *in-process open-source library* (MIT) that wraps individual tool calls inside
the agent process with deterministic policy evaluation, SPIFFE/DID identity
verification, and a tamper-evident audit log.

The three operate at fundamentally different layers — *programme*, *platform
gateway*, and *in-process runtime* — and they do not duplicate one another in
any consequential way. Their overlaps are partial and complementary: Citadel
governs the network and API plane; AGT governs the application plane inside the
agent; RVAS produces the human accountability structure across both. A customer
can run RVAS sessions and deploy Citadel without ever touching AGT. Where AGT
adds value in the RVAS context is conceptual enrichment (illustrating
deterministic policy enforcement) and optional evidence generation (audit logs,
`agt verify` output, red-team scan results). AGT is **not** a prerequisite for
any RVAS session as currently designed.

**Staged recommendation:** document the conceptual relationship now; optionally
run a static `govern()` demo in S3 or S5 as illustration; defer any
production-required AGT integration until the toolkit reaches GA and the
customer has confirmed their agent application architecture can accommodate an
in-process library.

## 1. Three-Way Model

### 1.1 RVAS AI Governance — Delivery Programme

RVAS AI Governance is an RVAS offering. It is a co-delivered, seven-session
curriculum in which a facilitator works with the customer's administrators
inside the customer's own tenant. The programme establishes ownership, reviews
controls, captures evidence, and assigns the work that remains. Every session
leaves durable, customer-retained artefacts: Infrastructure as Code, exported
policies, runnable scripts, evaluation pipelines, runbooks, and a readiness
scorecard.[^rvas-readme]

Sessions: S0 Foundations & Operating Model, S1 Identity, S2 Data & Compliance,
S3 Security Posture & Runtime, S4 Quality & Safety Evaluation, S5 Adversarial
Testing, S6 Control Plane & Operationalization.[^rvas-readme]

RVAS does not deploy software into the customer's agent codebase. It reviews
the evidence that existing platform and application controls produce.

### 1.2 Foundry Citadel Platform — Platform / Gateway

The Foundry Citadel Platform (`https://github.com/Azure-Samples/foundry-citadel-platform`)
is a Microsoft reference architecture for enterprise AI security, compliance, and
scale.[^ptg-citadel] It organises capabilities into four connected layers:

| Layer | Purpose | Typical technology |
|---|---|---|
| **Governance Hub** | Route approved AI calls; apply shared gateway controls | Azure API Management, Azure API Center, access/backend contracts |
| **AI Control Plane** | Observe, trace, evaluate AI behaviour | Microsoft Foundry, evaluation and observability services |
| **Agent Identity** | Associate agents with sponsors, lifecycle, access context | Microsoft Entra Agent ID, Microsoft Agent 365 |
| **Security Fabric** | Protect data; respond to security and runtime-safety risk | Microsoft Defender, Microsoft Purview, Microsoft Entra, Content Safety |

The **AI Hub Gateway** (`https://aka.ms/ai-hub-gateway`, `citadel-v1` branch) is
the deployable accelerator for the Governance Hub layer. It includes an APIM AI
gateway, API Center registry, access contracts, gateway safety and PII-masking
patterns, Entra/JWT authentication, telemetry, and private-networking
options.[^ptg-accelerator] Citadel is not a deployment package itself; it is a
reference architecture that points to deployable accelerators.

The AI Governance programme does not rebuild Citadel capabilities. It assigns
owners, reviews evidence, and records the decisions and gaps that follow.[^ptg-programme-use]

### 1.3 Agent Governance Toolkit (AGT) — In-Process Runtime

> ⚠️ **Public Preview.** All AGT releases are Microsoft-signed
> production-quality public previews that *may have breaking changes before
> GA*.[^agt-changelog] Do not treat AGT as a production baseline without
> validating against your specific environment.

AGT (`https://github.com/microsoft/agent-governance-toolkit`) is an MIT-licensed,
open-source library with zero Azure/Microsoft dependencies in its core
packages.[^agt-limitations-sec5] It operates *inside the agent application
process* — not at the network or gateway layer.

**Core mechanism:** the `govern()` function wraps any tool call. Before the
model's intent reaches the wire, deterministic application-layer code evaluates
a YAML (or OPA/Cedar) policy and either allows, denies, or routes to human
approval. Actions the AGT kernel denies are *structurally impossible to
execute*, not merely unlikely.[^agt-readme]

**Key capabilities:**

| Capability | AGT component | Notes |
|---|---|---|
| Policy evaluation | `govern()` / `PolicyEvaluator` / YAML | <0.1 ms per evaluation[^agt-limitations-perf] |
| Tool allow/deny list | `createGovernedTool` | Per-tool rate limits |
| In-process identity | SPIFFE/DID (`did:mesh:*` or `did:agentmesh:*`) | DID method inconsistency across SDKs[^agt-limitations-did] |
| Inter-agent trust | DID-based trust gate | Challenge-response handshake |
| Tamper-evident audit | Merkle/SHA-256 hash chain | Records attempts, not outcomes[^agt-limitations-audit] |
| Anomaly / rogue detection | `AgentBehaviorMonitor` | Quarantine on threshold breach |
| Circuit breaker / rate limit | `_circuit_breaker_impl.py` | Cascade failure protection |
| MCP Security Gateway | `mcp_gateway.py` | Tool poisoning, drift, typosquatting detection |
| PromptDefense Evaluator | `prompt_defense.py` | 12-vector prompt injection audit |
| CLI governance tooling | `agt verify`, `agt red-team scan`, `agt lint-policy` | CI gate integration |

**Language support:** Python (full stack), TypeScript/Node, .NET, Rust, Go.
Python v4.1.0 consolidates 45 → 5 distributions; the old `agent-os-kernel`
emits a `DeprecationWarning`.[^agt-readme-pypi]

**OWASP Agentic compliance:** AGT self-assesses 7/10 Full, 3/10 Partial
(ASI04 supply chain: no SBOM; ASI06 memory: no sandbox; ASI09 human approval:
no UI-level dialogs). This is an *internal self-assessment, not a validated
certification or third-party audit*.[^agt-owasp-disclaimer]

## 3. Overlap / Non-Overlap Table

| Dimension | RVAS (Programme) | Citadel (Gateway) | AGT (In-Process) | Overlap / Verdict |
|---|---|---|---|---|
| **Policy enforcement point** | None (reviews evidence) | APIM gateway policies at HTTP layer | `govern()` at tool-call layer inside process | **No conflict** — different enforcement planes |
| **Identity model** | Reviews Entra Agent ID / Agent 365 records | Entra/JWT authentication at gateway | SPIFFE / DID (`did:mesh:*` or `did:agentmesh:*`) | **Partial overlap** — different identity scopes; Citadel uses Azure AD tokens; AGT uses open DID standards. No integration bridge currently exists. |
| **Audit / evidence** | Captures and records evidence across sessions | APIM telemetry, API Center access logs, Foundry traces | Merkle-chained in-process audit log (attempts, not outcomes) | **Complementary** — Citadel produces platform-layer telemetry; AGT produces process-layer decision records; RVAS consumes both |
| **Prompt injection detection** | Reviews Prompt Shields configuration (S3) | Content Safety / Prompt Shields at gateway | `PromptDefenseEvaluator` (12-vector); `blockedPatterns` in middleware | **Partially overlapping** — Citadel screens at gateway before request reaches agent; AGT screens inside agent process. Citadel does NOT cover indirect injection after retrieval; AGT's middleware checks inbound but has acknowledged gap for context poisoning (ASI06)[^agt-owasp-coverage] |
| **Supply-chain / SBOM** | Not directly addressed | API Center tool registry | Policy YAML tool pinning; **no SBOM generation** (ASI04 gap)[^agt-owasp-asi04] | **Gap in AGT**; Citadel API Center provides registry but not full SBOM |
| **Human-in-the-loop** | Facilitated review in every session | Not in scope | `require_approval` in policy YAML; **no UI approval dialogs** (ASI09 partial)[^agt-owasp-asi09] | RVAS provides the human process; AGT provides a technical hook; neither provides a turnkey UI |
| **Red-team / adversarial** | S5 uses PyRIT + AI Red Teaming Agent | Not in scope | `agt red-team scan` CLI (prompt injection audit) | **Complementary** — `agt red-team scan` could augment PyRIT findings in S5 |
| **Lifecycle / registry** | S6 reconciles Agent 365 / Entra / API Center records | API Center registry, access contracts | Shadow AI Discovery (`agent-discovery`) | **Complementary** — different scopes: AGT discovers unregistered process-level agents; S6 reconciles platform registry records |
| **Compliance mapping** | NIST AI RMF, ISO/IEC 42001, EU AI Act (illustrative) | Not formally mapped | OWASP Agentic Top 10 self-assessment; AARM, ATF badges | **Different frameworks** — not directly competing |
| **Deployment prerequisite** | None — customer's environment | Customer deploys Citadel accelerator separately | Customer installs AGT in agent code (`pip install`) | **No overlap** — all three are independently deployable |
| **Vendor dependency** | Microsoft-delivered programme | Azure (APIM, API Center, Entra, Defender…) | **Zero Azure / MS core dependency**[^agt-limitations-sec5] — runs on any cloud or on-prem | AGT is cloud-agnostic; Citadel is Azure-native |
| **Known gaps (AGT)** | Not applicable | Not applicable | No SBOM, no memory sandbox, no UI approval, no outcome verification, no knowledge/data provenance governance, credential persistence gap, init bypass risk, cross-session attack surface[^agt-limitations] | AGT acknowledges 12 design boundaries; these are relevant when evaluating it as a production control |

## 4. Integration Caveat

> ⚠️ **AGT–Citadel reference artefacts exist but must not be treated as a
> production baseline without validation.**

The RVAS Platform Technical Guide references both AGT and Citadel as
complementary capabilities for the platform team.[^ptg-agt-mention] However,
no verified AGT–Citadel integration example was found in either repository
during this research (searched `microsoft/agent-governance-toolkit` examples
directory and `examples/demos/` tree as of commit
`b680c49cc956727c5249771ddba7ee21a635a676`). The demos available include
`governance-dashboard`, `governed-agent-in-10-min`, `maf-integration`,
`openclaw-governed`, and `physical-attestation-governed` — none are
Citadel-specific.[^agt-examples-demos]

If future AGT or Citadel releases publish an explicit integration guide or
example, it should be reviewed and validated before use in a customer delivery.
Until then:

1. Treat AGT and Citadel as independently deployable — composing them requires
   customer engineering effort.
2. The RVAS programme does not require AGT; Citadel does not require AGT.
3. Any live demonstration using AGT in an RVAS session must be clearly labelled
   as illustrative of the pattern, not as the validated customer architecture.

## 6. Staged Recommendation

### Stage 1 — Document now (this report)

Record the conceptual relationship in the RVAS reference materials. Update the
platform capability landscape in S0 to include AGT as an *optional in-process
runtime layer* alongside Citadel (gateway layer) and the Microsoft cloud
services (identity, data, security layers). No customer action required.

### Stage 2 — Optional static demo (any session S3/S5)

Prepare a self-contained, offline `govern()` demonstration:

```python
# Illustrative only — not a production deployment
from agentmesh.governance import govern

def send_email(to: str, body: str) -> str:
    return f"Email sent to {to}"

safe_send = govern(send_email, policy="demo-policy.yaml")
safe_send(to="user@example.com", body="Hello")   # allowed
safe_send(to="all@example.com", body="DROP TABLE") # GovernanceDenied
```

Pair with `agt verify --evidence ./demo-evidence.json` to show the CLI gate
pattern. Label the demo explicitly as "illustrative of the in-process
governance pattern, not a validated architecture for this engagement."

### Stage 3 — Defer production / required integration

Do not add AGT as a required component of any RVAS session or as a mandatory
customer deliverable until:

- [ ] AGT reaches GA (breaking-change risk resolved)
- [ ] Customer's agent application architecture is confirmed to be compatible
      with an in-process Python/TS/.NET library
- [ ] AGT–Citadel integration path is validated and documented by Microsoft
- [ ] Customer engineering team has reviewed AGT's 12 known limitations
      (`LIMITATIONS.md`) and accepted residual risks
- [ ] AGT initialization and policy-loading configuration has been verified
      (`agt doctor` clean; strict/deny-by-default mode confirmed)[^agt-limitations-init]

## 7. Risks and Decision Gates

| Risk | Severity | Gate / Mitigation |
|---|---|---|
| **AGT Public Preview — breaking changes** | High | Wait for GA before any production commitment. Monitor `CHANGELOG.md`. |
| **DeprecationWarning in `agent-os`** | Medium | Use `agent-governance-toolkit-core` (`[full]` extra) not `agent-os-kernel`. Verify with `agt doctor`. |
| **DID method inconsistency across SDKs** | Medium (cross-SDK deployments) | Use wildcard DID matching in policies; standardise SDK family for identity generation.[^agt-limitations-did] |
| **OWASP self-assessment ≠ certification** | Medium | Disclose to customer that AGT's compliance badges are self-assessments. Do not present as third-party audit. |
| **Fail-open when no policies loaded** | High | Production deployments must use strict/deny-by-default mode. Run `agt audit` to verify loaded policies.[^agt-limitations-init] |
| **Knowledge governance gap** | Medium | Combine AGT with a data classification layer; use egress policies and blocked_patterns for PII. Do not represent AGT as covering S2 data controls.[^agt-limitations-knowledge] |
| **Cross-session attack surface** | Medium | AGT does not yet implement workflow-level or cross-session policy evaluation. Relevant for agents with persistent memory.[^agt-limitations-crosssession] |
| **No AGT–Citadel integration example** | Low–Medium | Treat compositions as requiring customer engineering; do not demo as a ready reference architecture. |
| **Citadel is a reference architecture** | Low | Confirm `citadel-v1` branch deployment status with platform team before any S3/S6 evidence depends on it.[^s3-readme-track-b] |
| **Customer agent not AGT-compatible** | Low | AGT requires an agent application codebase. Verify applicability before recommending installation in any session. |
